# Notion 채용 공고 추천 자동화

매일 아침(약 07:00-08:00 KST) GitHub Actions가 원티드/사람인/잡코리아/직행(zighang.com) +
사용자가 지정한 관심 기업 채용 페이지를 스크래핑하고, Notion "설정" DB의 조건으로
필터링·랭킹해 상위 신규 10건을 Notion "추천 공고" DB에 누적 기록합니다.

이 피드는 **누적형 워치리스트**입니다: 하루 상위 10건은 그날의 *신규 진입 캡*이지,
전체 목록의 스냅샷 크기가 아닙니다. 기존 행은 매일 지워지지 않고 그대로 유지되며, 마감이
**긍정적으로 확인된** 경우에만(상세페이지 재요청 결과 404/마감 마커 등) Notion에서
아카이브(소프트 삭제)됩니다. 즉 이 DB는 시간이 지날수록 계속 쌓이는 목록이며, "매일
정확히 10개만 보이는 롤링 리스트"가 아닙니다. 스크래핑이 실패하거나 사이트 구조가
바뀌어도 기존 행이 실수로 삭제되는 일은 없습니다(마감 오인으로 인한 데이터 파괴를
막기 위한 설계입니다).

## 1. Notion 설정 (최초 1회)

이미 아래 두 DB가 워크스페이스에 생성되어 있습니다:

- **추천 공고** DB (data source id: `688618c7-0f3c-47b2-8fa4-b3bff7dc77fd`)
- **설정** DB (data source id: `107e6edc-31e6-438f-95d1-33e9eb743103`)

진행할 작업:

1. [Notion Integrations](https://www.notion.so/my-integrations)에서 Integration을
   생성하고 Integration Token(`secret_...`)을 발급받습니다.
2. 두 DB 각각에서 우측 상단 `...` → `Connections`(연결 추가) → 방금 만든 Integration을
   추가해 접근 권한을 부여합니다. (두 DB 모두 연결해야 합니다.)
3. **설정** DB에는 `기본 설정 (이 행 하나만 사용하세요)`라는 행이 이미 하나 들어 있습니다.
   이 행을 열어 실제 값으로 채워주세요:
   - **키워드** (필수, 최소 1개): 매칭할 키워드. 비어 있으면 파이프라인이 즉시 에러로
     중단됩니다.
   - **직무 / 경력 / 지역 / 채용유형** (선택): 비워두면 해당 조건은 전체 허용으로
     처리됩니다.
   - **관심기업** (선택): 회사명만 입력합니다 (URL이 아님 — 아래 3번 참고). 이 목록에
     없는 회사는 스크래핑되지 않습니다.

   이 DB는 **반드시 행이 하나만 있어야 합니다** — 행이 0개거나 2개 이상이면 파이프라인이
   에러로 중단됩니다(fail-closed).

## 2. 관심 기업 채용 페이지 URL (`company_urls.json`)

설정 DB의 **관심기업** 다중 선택 속성은 회사 이름만 저장할 수 있고 URL은 저장할 수
없습니다. 그래서 회사명 → 채용 페이지 URL 매핑은 리포지토리 루트의 `company_urls.json`
파일로 관리합니다 (현재는 `{}` 빈 상태로 커밋되어 있습니다). 이 파일을 직접 편집해서
실제 항목을 추가하세요. 예:

```json
{
  "딥엑스": "https://deepx.career.greetinghr.com/ko",
  "Nota": "https://career.nota.ai/ko",
  "모빌린트": "https://mobilinthire.career.greetinghr.com/ko"
}
```

(위 3개는 실제로 검증된 예시로 이미 커밋되어 있습니다 — 다른 회사를 추가하려면 아래
설명대로 항목을 더 넣으면 됩니다.)

- Greenhouse(`boards.greenhouse.io`), Lever(`jobs.lever.co`), **GreetingHR**(국내 ATS —
  `*.career.greetinghr.com` 뿐 아니라 회사 자체 커스텀 도메인에 붙는 경우도 페이지 내용을
  보고 자동 인식됩니다) 채용 페이지는 전용 파서로 지원됩니다. 그 외 페이지는 범용
  목록/테이블 파서로 최대한 시도하되, 지원되지 않는 구조라면 해당 회사만 건너뛰고 경고
  로그만 남깁니다(전체 실행은 계속 진행됩니다).
- 설정 DB의 **관심기업**에 이름을 넣었는데 `company_urls.json`에 매핑이 없으면, 해당
  회사는 조용히 스킵됩니다(경고 로그는 남습니다).
- 이 파일은 반드시 **커밋되어 있어야** 합니다 — GitHub Actions는 리포지토리에 커밋된
  내용만 읽습니다.

## 3. GitHub Actions Secrets

리포지토리 `Settings` → `Secrets and variables` → `Actions`에서 아래 3개를 등록합니다:

| Secret | 값 |
|---|---|
| `NOTION_TOKEN` | 1번에서 발급받은 Integration Token |
| `RECOMMENDATION_DB_ID` | `688618c7-0f3c-47b2-8fa4-b3bff7dc77fd` |
| `CONFIG_DB_ID` | `107e6edc-31e6-438f-95d1-33e9eb743103` |

워크플로우는 `.github/workflows/daily-job-recommend.yml`에 정의되어 있으며, 매일
`06:55 KST` (cron `55 21 * * *` UTC)에 자동 실행되고, `Actions` 탭에서
`workflow_dispatch`로 수동 실행도 가능합니다.

## 4. 로컬 실행 / 테스트

```bash
pip install -r requirements.txt

# 테스트 실행 (Notion/HTTP 호출은 전부 모킹되어 있어 네트워크 접근이나 실제
# 토큰이 필요 없습니다)
pytest

# 실제 파이프라인 로컬 실행 (실제 Notion Token/DB에 기록됩니다)
NOTION_TOKEN=secret_... \
RECOMMENDATION_DB_ID=688618c7-0f3c-47b2-8fa4-b3bff7dc77fd \
CONFIG_DB_ID=107e6edc-31e6-438f-95d1-33e9eb743103 \

```

첫 로컬 실행 후 재실행해서 추천 공고 DB에 중복 행이 생기지 않는지(URL 기준 upsert가
정상 동작하는지) 확인하는 것을 권장합니다.

## 5. 동작 방식 요약

1. **피드 상태 로드**: 추천 공고 DB의 기존 행(활성 + 아카이브)을 URL 기준으로 불러옵니다.
2. **Discovery**: 4개 소스 + 관심 기업 페이지를 스크래핑합니다. 개별 소스가 실패해도
   나머지는 계속 진행됩니다.
3. **Liveness Recheck**: 마감 임박(7일 이내) 또는 상시채용(주 1회 주기) 행의 실제
   상세페이지를 재요청해, 404/마감 마커 등 **긍정적 증거**가 있을 때만 "마감 확인됨"으로
   표시합니다.
4. **매칭**: 신규 발견 URL만 키워드/조건으로 필터링하고 점수를 매겨 상위 10건을 뽑습니다.
   기존 행은 재매칭하지 않습니다(매칭키워드/관련도점수는 최초 진입 시점 값을 그대로
   유지합니다).
5. **Notion 동기화**: 신규 10건은 새 행 생성, 아카이브된 행이 재발견되면 복구(un-archive)
   + 전체 필드 재평가, 기존 활성 행은 D-day/모집상태만 갱신, 마감 확인된 행은 아카이브.
   단 **어떤 소스의 discovery가 이번 실행에서 예외를 던졌다면, 그 소스가 원래 등록한
   행에 대한 아카이브는 이번 실행에서 전부 건너뜁니다** (스크래핑 실패를 마감으로
   오인해 데이터를 파괴하지 않기 위한 안전장치입니다).

기존 "취업 지원 현황" 템플릿(별도 DB)은 이 자동화의 어떤 코드 경로에서도 읽거나 쓰지
않습니다.

## 6. 소스별 수집 방식 (실제 사이트로 검증됨)

4개 소스 모두 실제 사이트에 직접 접속해 검증한 방식으로 구현되어 있습니다(더 이상
추측한 CSS 셀렉터가 아닙니다):

- **원티드**: 목록 페이지가 클라이언트 렌더링(React)이라 서버 HTML에 공고 데이터가
  없습니다. 대신 공개 목록 JSON API(`/api/v4/jobs`)를 직접 호출합니다.
- **사람인**: 검색 결과 페이지는 **키워드가 있어야만** 실제 결과를 서버 렌더링합니다
  (빈 검색어로는 "인기있는 채용정보" 추천 위젯만 나옵니다). 그래서 사람인만 다른
  소스와 달리 설정 DB의 **키워드**로 직접 검색해 수집합니다(키워드별로 검색 후 URL
  기준 중복 제거, 최대 5개 키워드까지만 사용).
- **잡코리아**: `/Recruit/Joblist` 결과 테이블을 파싱합니다. 실제 페이지네이션은
  세션/리퍼러 상태가 필요한 AJAX 엔드포인트라 단순 GET으로는 접근할 수 없어(확인됨:
  `Page_No` 파라미터를 바꿔도 동일한 첫 페이지가 반환됨), 기본 페이지 1개만 수집하는
  제약이 있습니다.
- **직행**: 목록 페이지가 RSC(스트리밍) 렌더링이라 서버 HTML에 공고 데이터가 없고,
  `/api/` 경로는 `robots.txt`가 명시적으로 차단합니다. 대신 `robots.txt`가 안내하는
  공개 사이트맵(`/seo/sitemap/sitemap-index.xml`)에서 최신 공고 상세페이지 URL을
  찾고, 각 상세페이지에 포함된 표준 schema.org `JobPosting` JSON-LD를 파싱합니다(요청
  수를 제한하기 위해 최근 사이트맵 일부 + 최대 40건까지만 처리).
- **관심기업**: Greenhouse/Lever는 각각 공식 목록 JSON API(`boards-api.greenhouse.io`,
  `api.lever.co`)를 사용합니다(HTML 스크레이핑보다 훨씬 안정적입니다). GreetingHR은
  전용 API가 없어서 채용 목록 페이지의 `__NEXT_DATA__` 안에 내장된 공고 목록 데이터를
  파싱합니다(도메인이 아니라 페이지 내용으로 자동 인식되므로 커스텀 도메인에서도
  동작합니다). 그 외 페이지는 기존과 동일하게 범용 HTML 목록/테이블 파서로 최대한
  시도합니다.

각 사이트는 마크업/API를 예고 없이 바꿀 수 있으므로, 이 문서화된 방식도 시간이 지나면
다시 깨질 수 있습니다 — 실패 시 해당 소스만 건너뛰고 경고 로그를 남기는 기존 안전장치
(본문 5번 참고)가 여전히 적용됩니다.
